## 6. The project's strengths - from the build itself

These are not claims. Each is drawn from the source code and the design artefacts.

| Design system (Stitch) | complete, brand-accurate |

### 6.2 Three complete role pathways - one platform

This is the strongest structural fact about the project. Most local commerce tools give you a shop. This gives three linked operating surfaces in one build.

| Pathway | Bottom navigation |
|---|---|
| **Customer** | Home - Categories - Cart - Search |
| **Store Admin** | Dashboard - Finances - Store View |
| **Driver** | Runs - Active - Earnings - Chat |

All three fork from a single role-selection screen and share one codebase.

### 6.3 A complete last-mile delivery module already built

This is directly relevant to the moped fleet, because the software side of a courier operation **already exists**.

**Driver routes present:** `driver-start`, `kyc`, `driver`, `queue`, `earnings`, `active`, `delivered`, `driver-fees`, `driver-apply`, `drivers-admin`

**The driver data model in the code carries:**

```
kycStatus: 'verified'
vehicle: { type, plate, year }
earnings: { today, week, month }
deliveries: [ { id, store, status, eta, address } ]
```

**Real delivery records already modelled with distance and fee:**

```
{ id: 'D-4471', store: 'Kingdom Organics', area: 'Tralee Town', km: 3.2,
  fee: 6.50, tip: 1.50, status: 'delivered' }
{ id: 'D-4472', store: 'Yousef Spice',      area: 'Oakpark',     km: 4.8, ... }
{ id: 'D-4474', store: 'Kerry Produce',     area: 'Manor West',  km: 6.4, ... }
```

**What this means practically:** a rider fleet does not need new software invented. It needs vehicles and onboarding into a driver module that already tracks the vehicle, the runs, the distance, the fee and the payout.

### 6.4 AI document scanning already integrated

`server/ai.js` is a working, provider-agnostic document reader:

| Capability | Present |
|---|---|
| Invoice / docket / price-list extraction | **yes** |
| Demo mode (works with no key) | **yes** |
| Local model endpoint supported | **yes** - `127.0.0.1:11434` |
| Vision model support | **yes** |
| Output normalised and clamped before use | **yes** |

**Why this matters for a local marketplace:** small producers hand over paper invoices and price lists. This turns a photograph into structured line items. That is the single most labour-saving piece for onboarding suppliers who are not digital.

### 6.5 Multi-vendor, not single-shop

The store admin pathway includes distributors, suppliers, certificates, services, guest codes and deals admin. That is the shape of a **marketplace serving multiple local producers**, not one shop's till.

### 6.6 Offline-capable installable app

It is a PWA with a service worker, installable to a home screen. Rural delivery areas have poor signal; a browser-only site fails there.
